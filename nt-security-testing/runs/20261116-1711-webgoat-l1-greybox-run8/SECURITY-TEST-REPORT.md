## 3. Findings

### F-01 - Session cookie lacks Secure and SameSite attributes (Medium)

**ASVS:** V3.3.1, V3.3.2 - cookie Secure and SameSite attributes.

The successful login response sets `JSESSIONID` over HTTP with `HttpOnly`, but the captured `Set-Cookie` field has no `Secure` or `SameSite` attribute. The same trace shows the login request and redirect use plaintext HTTP; no HTTPS upgrade was observed on this flow.

Request (password redacted in accordance with the intake):
```http
POST /WebGoat/login HTTP/1.1
Host: 10.242.10.31:8007
Content-Type: application/x-www-form-urlencoded

username=xtbuiquang&password=[REDACTED-TEST-PASSWORD]
```

Response (session-token value omitted from this report excerpt; full raw response is in the cited internal evidence):
```http
HTTP/1.1 302
Set-Cookie: JSESSIONID=[session token]; Path=/WebGoat; HttpOnly
Location: http://10.242.10.31:8007/WebGoat/welcome.mvc
Content-Length: 0
Date: Mon, 16 Nov 2026 10:17:20 GMT
```

The cookie lacks the Secure and SameSite attributes. `HttpOnly` was present and is separately recorded as a PASS for V3.3.4; it does not protect the token from plaintext transport or provide SameSite behavior.

- **Impact:** A network observer on the traffic path could capture credentials or the session token; the absent SameSite setting also leaves browser cross-site request behavior less constrained. No credential interception or CSRF exploit was attempted.
- **Remediation:** Serve the application through HTTPS and redirect HTTP to HTTPS before authentication; set `Secure` and an application-appropriate `SameSite` value on the session cookie, while retaining `HttpOnly`.
- **Evidence:** `evidence/http/04-login-post-redacted.txt`.
- **Confidence:** 9/10; the response directly shows the cookie attributes and the request used HTTP.

### F-02 - Browser security headers absent on the login response (Medium)

**ASVS:** V3.4.3, V3.4.4, V3.4.6, V3.4.7, V3.4.8 - Content Security Policy, nosniff, frame-ancestors, CSP violation reporting, and Cross-Origin-Opener-Policy.

The raw `GET /WebGoat/login` response is HTTP 200 and includes content type/language, transfer encoding, and date headers, but no CSP, X-Content-Type-Options, or COOP. Since there is no CSP header, there is also no `frame-ancestors` directive or CSP violation-reporting location in this response. This finding is limited to the captured login response; other routes were not checked for these headers.

Request:
```http
GET /WebGoat/login HTTP/1.1
Host: 10.242.10.31:8007
User-Agent: curl/8.21.0
Accept: */*
```

Response headers:
```http
HTTP/1.1 200
Content-Type: text/html;charset=UTF-8
Content-Language: en
Transfer-Encoding: chunked
Date: Mon, 16 Nov 2026 10:15:52 GMT
```

- **Impact:** The tested login page lacks browser-side defense-in-depth against script injection, MIME sniffing, and framing. No exploit or clickjacking proof was attempted.
- **Remediation:** Configure a suitable CSP including `object-src 'none'`, `base-uri 'none'`, and an explicit `frame-ancestors` policy; add `X-Content-Type-Options: nosniff` and an appropriate `Cross-Origin-Opener-Policy` value, then verify all document responses.
- **Evidence:** `evidence/http/02-login-route-raw.txt`.
- **Confidence:** 9/10; the complete captured response header block contains no listed headers.
